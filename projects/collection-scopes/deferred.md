# Deferred

Items found during the project that are out of its scope. Each says what to do later and why it was not done here.

- **Two deferred-at-lowering callbacks for indexes have different shapes.** In `packages/2-sql/2-authoring/contract-ts`, `DeferredIndexExpression` carries its own `fields`, while a deferred `options` function on `IndexConstraint` receives the columns of the index's `fields`, and no source code produces a deferred expression any more. Later: unify them into one `resolve(columns)` that returns `{ options?, expression? }`, or remove `DeferredIndexExpression` if no extension package uses it. Not done because unifying them changes an exported authoring interface the weighted full-text index does not need.
- **The SQL family builds a wrong intermediate schema node for a `fullText` index.** `contractNamespaceToSchemaIR` in the SQL family turns a `fullText` index into an index over its columns with the definition as storage options. It is correct only because the Postgres conversion replaces the node. No other caller exists today. Later: let the family conversion take an index conversion from the target, so the target builds the node once. Not done because it changes the family's conversion interface for every target.
- **Two checks that a full-text index covers text columns.** `@@fullTextIndex`, the TypeScript `fullTextIndex` helper and loading a contract check the `textual` trait against the Postgres target's built-in codecs; the index type registry's `columnTraits` checks the contract's composed codec lookup at contract build. They agree today, and would disagree if an extension package added a textual codec. Later: have the two authoring surfaces rely on `columnTraits`, keeping their own message only for a better source location. Not done because nothing registers an extra textual codec today.
- **A member on the ORM client collides with a contract namespace of the same name.** The client object returned by `orm()` holds one member per namespace next to its own methods, so a contract with a namespace named `scope` shadows the client's `scope` method and the application cannot make a scope for any model. Every future client member has the same problem. Later: put namespaces or the client's methods under their own member so names cannot collide. Not done because no contract names a namespace `scope` today and the change touches every call site that reads `db.orm.<namespace>`.
- **A search document is not an expression of its own.** For slice 4. `fullTextMatches` and `fullTextRank` in `packages/3-targets/3-targets/postgres` take either a textual column or weight groups of columns as their first argument, and the descriptor still declares a textual receiver: the first column becomes the operation's receiver and the other columns are appended after the fixed arguments. ADR 260's scope helper builds a document with `searchDocument(tableName, index.options)` and passes it to these operations. Later, before slice 4 builds on these forms: make the search document a first-class `tsvector` expression, built by a receiver-less operation from weight groups through the same renderer, and give `fullTextMatches` and `fullTextRank` forms that take a `tsvector`. Not done in slice 3 because the column forms serve the slice, and the parameter is named `document` with a doc comment saying the receiver may be a search document.

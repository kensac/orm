# System design review: TML-3443, the Postgres runtime driver returns every column as server text

Range: `origin/main...HEAD` on `leibniz-53/postgres-driver-text-only` (five commits, including 7e15f67f0b and 31cc56e942 from prisma/orm#30582). Expectation sources: `wip/drive/TML-3443/spec.md`, `wip/drive/TML-3443/dispatch-1-report.md`, the TML-3443 summary, ADR 251 and the driver README.

## Problem and new guarantee

Before this branch the runtime driver let `pg` parse most columns and returned server text only for an allowlist: temporal scalars, the 28 array OIDs that `pg-types` registers, and (after #30582) `json` and `jsonb`. Codecs then decoded a second time, so each Postgres codec had to accept both a `pg`-parsed value and text. The `jsonb` case showed why this is wrong: `pg` turned the stored JSON string `"hello"` into `hello`, and arktype-json could not tell a parsed JSON string from JSON text.

The new guarantee: rows returned by the runtime driver's `query` (buffered, cursor and named cursor paths) carry the server's text output for every column. `pg` parses nothing. The codec for each column owns decoding. The control driver keeps its old policy (`pg` parsing, with array OIDs as text). arktype-json now always parses a string wire as JSON text and then validates the parsed value, which is what `pg/json@1` and `pg/jsonb@1` already do.

The direction is right. It removes a hand-maintained allowlist, removes a heuristic from arktype-json, and gives every Postgres codec one input shape at runtime. The driver diff is three lines and matches the spec exactly.

## Subsystem fit

The layering in `docs/architecture docs/subsystems/5. Adapters & Targets.md` says the driver owns transport and the runtime composes codecs from adapters and packs. ADR 030 defines the wire value as "the value as returned by the driver before transformation" and lists driver native mapping as the last fallback. This branch moves the Postgres driver to the thinnest possible position: it returns transport text and does no type mapping. That fits the layering better than before, because type knowledge now lives only in codecs, which the target owns.

No code in the diff branches on target. Nothing is added under `packages/1-framework`. The diff removes one explanatory comment (the "try the raw wire first" block in arktype-json and the JSON comment from #30582) and adds none. The package dependency from arktype-json tests to `@internal/driver-postgres` already existed.

## Boundary correctness

The guarantee "codecs own decoding" holds only if every consumer of runtime driver rows decodes through a codec. Two runtime consumers do not, and the PR does not mention either.

1. The runtime marker check. `packages/3-targets/6-adapters/postgres/src/core/adapter.ts` lines 58 to 77 hand the runtime queryable to `PostgresControlAdapter.readMarkerDiscriminated`. That code reads `prisma_contract.marker` without codecs and validates the row with `ContractMarkerRowSchema` in `packages/2-sql/9-family/src/core/verify.ts` lines 74 to 83. Under the control policy `canonical_version` arrives as a number. Under `serverTextTypes` it arrives as a string such as `'1'`, and the schema (`'number | null'`) rejects it with `CONTRACT.MARKER_ROW_CORRUPT`. Every Postgres writer stores `null` today, so nothing fails now, but the same parsing code now receives two different wire shapes depending on which plane calls it. `meta`, `contract_json` and `updated_at` already tolerate strings, which is why the ports tests pass.
2. Projection items without a codec. `packages/2-sql/5-runtime/src/codecs/decoding.ts` lines 262 to 265 return the wire value unchanged when an alias has no codec. Before this branch such a column arrived as a `pg`-parsed number or boolean. Now it arrives as text. The implementer flagged this and found no failing case, but the guarantee now depends on an invariant (every runtime projection item carries a codec) that nothing enforces.

The asymmetry between the two policies is legitimate. The control plane reads catalog rows without codecs, so it needs `pg` parsing. The problem is that "control plane" and "codec-less reader" are not the same set: the marker reader is codec-less and runs on both planes.

## Naming and typology

`serverTextTypes`. Discriminator completeness: it is one of two policies, and the name says what it does (every value is server text). Consumer versus essence: named by essence. Concept versus mechanism: "types" is the `pg` option name (`CustomTypesConfig`), so it reads as "the `types` config that yields server text". Reads cold: yes. Keep it.

`controlTextTypes`. Named by its consumer (the control plane), not by what it does. Its sibling is named by what it does. So the pair fails the symmetry probe: a reader cannot tell from the names that one policy parses nothing and the other parses everything except arrays. The name also hides the behaviour that matters most, which is that it keeps `pg` parsing. A name such as `arrayServerTextTypes` (or `pgParsedScalarTypes`) states the behaviour, and the pair then reads as two points on one axis.

`server-text-types.ts`. The file holds both policies, and the second one mostly does `pg` parsing. The file name describes only one of its two exports. A name such as `type-parser-policies.ts` (or `row-parser-policies.ts`, matching the README heading "Row parser policy") covers both. Keeping both policies in one file is good: it puts the asymmetry side by side. The names are what hide it.

`PG_TYPES_ARRAY_OIDS`. Names what it is (the array OIDs that `pg-types` registers). Now used only by the control policy. The name is still correct. No change needed.

`serverText` (the identity parser). Fine.

## ADR and README review

Driver README, "Query Result Parser Policy" bullet and "Row parser policy" section (`packages/3-targets/7-drivers/postgres/README.md` lines 30 and 79 to 85). The new text states the guarantee in the right place and gives good examples (`t`, `\x0102`, `NaN`, `{a,b}`, quoted JSON strings). Three issues:

- It says "Every runtime row then goes through codec decoding". That is not true for the marker read and for codec-less projection items (see Boundary correctness).
- It says "Direct driver query consumers see the same server text strings". `explain` in `packages/3-targets/7-drivers/postgres/src/postgres-driver.ts` lines 336 to 357 passes no `types` option, so its rows use `pg` default parsing. That is a third behaviour, and the README says "Both policies".
- It does not use the codec vocabulary. ADR 030 calls the driver output the "wire value". Saying "the wire value of every Postgres codec at runtime is the server's text output for its type" would tie the README to the codec contract.

ADR 251. The edits fix a broken file link and replace stale sentences. Line 38 still says direct-query consumers "see registered array result columns as raw Postgres array text", which is now too narrow: they see every column as text. Line 34 says builtin numeric and boolean codecs accept raw spellings "as well as their existing native scalar wire values"; at runtime native scalar values no longer arrive, which belongs to the codec wire-type narrowing follow-up.

ADR placement. The driver-to-codec wire contract is now a system guarantee that every Postgres codec depends on, but it is recorded only as a side note in ADR 251, which is about list framing. ADR 030 still describes driver native mapping as the fallback. The natural home for a decision record is the codec wire-type narrowing follow-up, because that slice turns the guarantee into codec types.

## Test strategy adequacy

`driver.server-text.integration.test.ts` checks type breadth (bool, int2, int4, float8 with NaN and both infinities, bytea, oid, interval, json, jsonb) across three query paths and two bindings, and checks that `pg.types` globals are unchanged. The implementer showed it failing before the driver change. This is the right primary test.

`driver.json-text.integration.test.ts` (from #30582) is not a subset. It covers nine JSON values including JSON scalar strings whose quotes must survive (`"standard"`, `"123"`, `"null"`), and it covers `RETURNING` from `insert` and `update`. The server-text test covers only one JSON object and only `select`. The two files are complementary. `driver.temporal-text.integration.test.ts` is the third file in this family. The three files copy the same `openDriver` and `rows` helpers.

`server-text-types.lazy-pg-types.test.ts` now checks the runtime policy for an OID list including unknown OIDs, and keeps the array-set divergence check for the control policy. Good.

arktype-json: the unit tests now assert JSON text semantics, and the driver integration test shows the string-schema case failing before the change. Both tests call `codec.decode` directly, so neither checks the error envelope a user sees through the runtime (see D03).

Missing: no test reads the marker through the runtime path with a non-null `canonical_version`, and no test covers `explain` rows.

## Round 2: fix commits 5adeb11ba4 to 270215239e

Range reviewed: `03937ebf77..HEAD`. Inputs: `wip/drive/TML-3443/round-2-brief.md` and `wip/drive/TML-3443/dispatch-2-report.md`.

### Answers to the round 2 questions

1. Marker row fix. Converting integer text in `decodePostgresMarkerRow` is the right place for this PR. The adapter owns the marker read end to end, and that function already converts `invariants` from array text. It also accepts the control-plane shape (a number) unchanged, which is required while the two driver policies differ. One weakness: the marker table already declares `canonical_version` as an `int4` column (`packages/3-targets/6-adapters/postgres/src/core/marker-ledger.ts` line 26), so the reader parses with a hand-written regular expression the same text that the `int4` codec already parses (D15). The README now states the guarantee accurately and names the runtime marker check as a reader that parses text itself.
2. sql-builder fix. The fallback does not belong in `resolveSelectArgs`. It turns a `codecId` into a decode-time codec reference at the last moment, and for computed boolean expressions that `codecId` is the hard-coded `'pg/bool@1'` in the SQL family lane. On SQLite there is no descriptor for that id, so the fix very likely moves the failure from "returns raw text" to "throws `RUNTIME.CODEC_DESCRIPTOR_MISSING`" (D12). The field should carry a codec reference from the moment it is built, and the reference for a boolean result should come from the target, as aggregate results already do.
3. Interval decode order. Trying ISO 8601 first and then PostgreSQL text is safe, because PostgreSQL-style text never starts with `P`. The codec still describes one wire format: the text the server prints for an interval. The two branches are the two `IntervalStyle` settings the target reads (`iso_8601` and `postgres`). `pgIntervalCanonical` already reads the same two forms, so the decode now matches how the codec treats interval text elsewhere. The dispatch is written twice (D14). The non-string branch of `pgIntervalDecode` is now unreachable from the runtime driver (D10).
4. arktype-json error. Letting the `SyntaxError` escape matches `pg/json@1` exactly. Both codecs now share one contract for the wire value and one error contract for text that is not JSON. The runtime adds table, column, codec and wire preview. The same codec still throws a structured `RUNTIME.JSON_SCHEMA_VALIDATION_FAILED` that loses that context (D16). That predates this branch.
5. Upgrade fragment, README and ADR wording. All three are accurate and use the same vocabulary. The upgrade fragment lists each type's text form, and its detection patterns match codec authors and direct driver callers. No new findings.

## Round 3: commit 71c7819c78 (with a44ff2b705 and 65a348be53)

Judgement on `knowsCodec`. It is an acceptable shape for this PR, but it is a mechanism, not a concept. The concept that is missing is "which codec decodes a boolean predicate result on this target", and it would sit next to `aggregates` on `BuilderContext`. `knowsCodec` instead asks "can the runtime resolve this id", which works around the lane naming a Postgres codec id. It is acceptable now for three reasons. It is narrow. It is built from the codec descriptors the context already has. It restores exactly the behaviour SQLite had before this branch. It should be removed when the boolean result codec comes from the target.

Judgement on SQLite booleans. "Rows typed `boolean` hold `0` or `1` on SQLite" existed before this branch and deserves its own ticket. The public type tells users something false. It has the same cause as D12: `BooleanCodecType` is typed `'pg/bool@1'` across the SQL family lane's public expression surface. That is target vocabulary in a family-layer package.
